# 崽档备份与恢复重设计 · 审核稿

2026-09-08 · **产品规则已确认，账户级技术方案已修订，尚未实施**

建议采用「独立快照 + 媒体增量复用 + 整套数据切换」。用户仍然点击一次备份；每份快照在逻辑上包含全部资料，恢复不需要按顺序重放历史备份。

## 1. 当前问题与影响

| 问题 | 影响 | 证据 |
|---|---|---|
| 新数据库上传前删除旧立绘 | 新备份失败，上一份备份也可能无法完整恢复 | 已用实际 Dart 服务及假云存储复现 |
| 原生覆盖先删除目标再复制 | 复制中断时，旧数据库或 manifest 已消失；文件协调不等于多文件事务 | iOS/macOS 源码确认 |
| 复制进本机 iCloud 目录就提示已备份 | 离线、同步延迟、配额错误时，另一台设备可能还拿不到这份备份 | 源码无上传完成检查；未做真实断网实验 |
| 立绘只验证非空，不验证完整字节与内容 | 截断文件通过准备阶段，随后可能替换正常本地图片 | 4 字节变 1 字节的临时测试已复现 |
| Dart 接受空文档，原生层拒绝所有零字节文件 | 合法空文档无法正常恢复 | 原生函数提取测试 + 源码确认 |
| 页面持有任务和 busy 状态 | 返回后任务仍可能写入；再次进入可开启另一任务；超时不停止底层操作 | 源码与 Dart timeout 合同确认 |
| 依次替换立绘、资产、数据库 | 崩溃后可能只换了一部分；数据库换好后的清理异常还可能触发媒体回滚 | 源码路径确认，未注入断电实验 |
| manifest 损坏被当作不存在 | 部分错误会退化成不完整发现流程，无法清楚告诉用户备份是否损坏 | 源码确认 |
| 立绘按整个目录备份 | 未使用图片也占用云端空间 | 源码确认 |

完整定位和实验见 [现状审计](research/current-audit.md)。

## 2. 三种方案比较

| 方案 | 可靠性与成本 | 结论 |
|---|---|---|
| A. 保持单槽覆盖，补原子写、校验和锁 | 改动较小；多文件一致性、多设备覆盖和历史恢复仍难处理 | 只适合临时止血 |
| B. 独立快照 + 不可变媒体对象 | 新失败不覆盖旧；媒体可复用；需要清单、任务状态和安全清理规则 | **推荐** |
| C. 每次生成完整压缩包上传 | 数 GB 视频会反复上传、占多份空间 | 不采用；首版也不提供用户手动文件备份 |

用户已确认尚未统计数据量，按可能增长到数 GB 设计。保留媒体原图/原文件，不为备份压缩画质。

## 3. 推荐的用户体验

### 备份

1. 点击「备份到 iCloud」。显示本次角色数、文件数、资料总量；只备份已经保存的内容。
2. 显示「整理资料 → 准备文件 → 等待 iCloud 上传 → 确认完成」。有真实字节信息时才显示百分比；同步状态未知时显示等待原因。
3. 上传中可离开页面，回到页面能接着看进度。系统挂起后提示需要回到 App 继续确认，不承诺持续后台运行。
4. 完整上传由系统确认后，出现新的备份记录，标明时间、来源设备、角色数、大小。等待上传不能显示为「已备份」。
5. 新失败不影响之前完成的备份，可以重试未完成的任务。

### 恢复

1. 从备份记录中选择一份，不直接覆盖一个含义不明的「最新文件」。设备时间只用于展示，不作为覆盖优先权。
2. 下载并检查全部必需文件、数据库结构和版本；旧数据库先在临时数据目录中升级。
3. 准备完成后，显示将恢复的角色数、资产数，以及将替换的本机内容，用户再次确认。
4. 确认后短暂阻止本机写入并切换整套数据；随后重新打开数据库、刷新页面和图片缓存。
5. 保留恢复前的一份本机数据，可点击「恢复到上一次恢复前」。再次切换同样需要确认，且会替换这期间的编辑。

下载阶段离开页面不会自动进入覆盖。真正开始切换后短暂禁止取消；切换失败由启动恢复机制选择完整旧数据或完整新数据。

### 首版范围（用户已确认）

用户不需要手动导出完整备份文件和从文件恢复。首版专注 iCloud 备份与恢复，完整呈现数据范围、目录、时间、进度和结果；新界面不保留旧「保存到文件」入口。

### 全链路可视化（用户追加要求）

每份备份都能点开查看角色资料、文件清单和时间记录；备份和恢复有持续可回访的进度页，完成后有结果报告。页面明确区分完整资料总量、本次上传量与已完成量；上传完仍等待云端确认，下载完还需校验与用户确认。历史目录按备份时刻固定，不读取当前本机资料来“拼”历史名称。

详见 [全链路可视化交互方案](visual-experience.md)，包含内容目录、时间语义、进度来源和新增验收场景。本轮同时提供示例数据交互原型，仍不修改业务代码。

## 4. 必须成立的安全规则

- 同一份快照的数据库、清单和文件绑定在一起；不从云端散落文件拼凑不同时间的数据。
- 新内容写入新名字，发布后不可变；上一份快照不被新备份覆盖。
- 数据库用 SQLite 正式快照接口；文件以快照内的实际引用为准。
- 校验包含精确大小和 SHA-256；空文档合法，缺失文件不静默跳过。
- 只有所有内容可用并校验通过，才允许覆盖本机。
- 恢复切换和任务状态由应用级服务管理，不由页面生命周期决定。
- 失败原因分清未登录、等待同步、空间不足、文件缺失、内容损坏、版本不兼容和取消。
- iPhone 与 Mac 使用同一账户备份目录，共享最近 3 份名额；来源设备只作标签，文件写入仍使用独立名字。

这些规则是结合当前工程提出的设计，不把 iCloud 文件同步当成服务器端事务。

## 5. 空间和历史策略（用户已确认）

- 同一个 iCloud 账户合计保留最近 **3 份已完成备份**，所有设备共享这个名额。新备份完整确认后，才淘汰最旧的一份。
- 未变化的媒体可复用；导入时计算并缓存摘要，减少后续全量重复读取。物理占用仍取决于保留快照实际引用的原文件。
- 每台本机保留 **1 份恢复前副本**，并提供清理入口。恢复前展示额外空间需求，空间不足就停止。
- 同一账户使用统一保留集合和活动任务保护，清理前检查所有引用；不能由各设备根据不完整本地列表自行删除。
- 同步/清理延迟和旧版迁移残留可能暂时额外占用空间；与正常保留的 3 份备份分开展示。
- 首版不增加额外永久固定备份；损坏时先重试或换选其他有效备份，不提供部分恢复。

## 6. 旧版本与升级

- 新备份使用新目录及格式 v3；原来的 `ochome-backup` 按只读兼容处理。
- 支持现有格式 v1/v2、以及可验证的旧式无 manifest 备份；数据库 schema 3–8 在暂存区验证、升级后才切换。
- 旧备份缺少原始摘要，不能承诺追溯检测同大小篡改；明确标记「旧版备份，完整性保障有限」。现存 manifest 损坏与真正没有 manifest 必须区分。
- 更新版本/未知格式、缺失必需文件、解析失败均不能覆盖本机。
- 正常升级只初始化存储控制信息，不强制搬走当前所有媒体。首次成功恢复才切换到新数据目录。

## 7. 实施与验收

建议分四个检查点交付，详细执行顺序见 [实施计划](implement.md)：

1. 确认新格式与原生 iCloud 状态合同，固化已复现故障测试。
2. 完成应用级与账户级协调、引用快照、增量上传、统一历史及保留策略。
3. 完成暂存校验、目录切换、重启恢复、旧格式兼容和恢复前副本。
4. 完成全链路可视化界面及 iPhone/Mac 双设备验收。

必须测试：中断上传保住旧备份；截断及同大小损坏被拒绝；空文档可恢复；恢复每个切换点强制结束进程后数据不混用；离开/重进/取消不产生重叠写入；另一台设备能恢复；低空间和 iCloud 账号变化不丢数据。

## 8. 已确认规则与后续工作

已确认 B 方案的产品方向：账户合计 3 份云端备份、本机 1 份恢复前副本、严格校验后整份恢复、无手动文件备份、完整可视化。

账户合计需要调整原先按设备清理的技术方案。推荐增加仅保存目录/并发状态的 CloudKit 私有账户索引，大文件继续使用 iCloud Documents；不新增用户登录或自建后台。该技术修订需先做平台能力及双设备验证，见 [账户级保留方案](research/account-retention.md)。本轮没有修改业务代码、原生能力或云端配置。

完整格式、接口与故障处理见 [技术设计](design.md)，需求边界见 [PRD](prd.md)。后续为技术验证、实现与验收，不再重复确认已定的产品规则。

## 摘要计算性能优化

导入文件时边复制边计算 SHA-256，成功后存入本地索引。未改内容的文件后续备份主要比较索引并检查对象状态；真正上传与恢复写入时，在原本就需要的文件读取中校验实际字节。旧文件首次使用时补算，不在启动时阻塞全量扫描。技术边界与验证见 [摘要缓存方案](research/digest-caching.md)。
