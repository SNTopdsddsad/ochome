# 导入时计算摘要、后续备份复用缓存

2026-09-08 · 用户提出性能顾虑，并建议在文件存入本地时保存摘要、备份时与云端比较。本文件将该优化方向纳入方案；采用 SHA-256，不因缓存策略改用 MD5。仍为设计阶段，未修改业务代码或数据库。

## 1. 为什么这样做

每次备份都重新读取全部数 GB 原文件才能计算摘要，会产生与总字节数相关的耗时、磁盘 I/O 和 CPU 开销。导入本来就必须读取并复制文件，可以在同一条有背压的字节流中计算摘要，不额外打开源文件读第二遍。之后未变化文件的备份主要比较索引、检查存在性和版本信号，再复用有效云对象。

这减少重复读取，不代表哈希运算免费或对设备完全无影响。不能给出未经真机测量的“几秒内完成”保证。

## 2. 导入合同

1. `XFile.openRead()` 的每个字节块同时进入顺序写入和增量 SHA-256 计算；两者处理同一批字节，并遵守写入背压。
2. 不在主 UI isolate 做持续的大量摘要运算；使用一个有界 worker 或 native 后台执行。传入路径/任务标识，不把整个视频字节数组发给 worker。
3. 所有字节处理完、hash finalization、flush/close、精确长度检查、最终文件 rename 成功后，才登记有效摘要。
4. 取消、写入失败、长度不符、hash 未结束不能保存一条“有效指纹”。文件成功、派生缓存写入失败可以安全退化成未知摘要，后续补算；缓存不能成为孤儿文件删除的唯一依据。
5. 当前角色资产导入已经按流复制，适合接入此计算。立绘目前使用 readAsBytes 全量读入，实施时与同一流式保存工具统一，覆盖两类文件。

在写入流上计算的摘要记录导入内容的预期字节身份；它不是以后任何时刻磁盘内容仍完好的证明。

## 3. 本地数据库存储方式

推荐把它作为可重建的本地派生索引，复用 `storage-control/writer-ledger.sqlite` 的独立缓存表，不为可重建缓存修改角色/资产领域 schema。角色 SQLite 暂保持 schema 8；如果实施阶段改为在业务表中加列，必须另行递增 schema 并补迁移，不能默默加字段。

拟议表：

```text
file_fingerprints
  datasetId
  relativePath
  contentGeneration             # 受控的不可变文件身份
  algorithm = sha256
  digest                        # 64 位 hex
  bytes                         # 精确字节数
  observedMtime, fileIdentity?   # 缓存失效线索，不是内容证明
  recordedAtUtc
  origin = imported | backfilled | restoreVerified
  state = valid | unknown | stale
  UNIQUE(datasetId, relativePath)
```

云对象映射另外绑定 accountSession、writerId、objectId、摘要、字节数、已确认状态与可用的对象版本信息。本地文件摘要不能只按文件名做全局缓存；不同 dataset 下相同路径必须隔离。

## 4. 何时可以复用

| 场景 | 摘要处理 |
|---|---|
| 刚导入并完整落盘 | 使用同一条复制流计算的摘要 |
| 只改显示名称、所属说明或其他元数据 | 不重算原文件摘要 |
| 替换/编辑原文件内容 | 写新不可变文件身份并计算新摘要，不沿用旧值 |
| 本地身份、路径、大小/版本信号异常 | 缓存失效；不能继续用旧摘要跳过处理 |
| 历史文件没有摘要 | 第一次需要时后台补算并持久化；不在启动时全量阻塞 |
| 整套恢复切换 dataset | 不沿用旧根同名缓存；新文件经实际字节校验后建立新缓存 |
| 缓存损坏/丢失/算法不同 | 安全重建，不能从显示名称猜测匹配 |

快路径限定于 App 管理的不可变原件及受控写入历史。大小/mtime/身份信号可发现部分变化，但即使都相同，也不能排除静默位损坏；因此“复用了记录”不能显示成“刚刚重新检查过所有原文件”。

## 5. 备份与云端比较

- 先读取本地摘要索引及受校验清单/账本中的云端摘要，用 `(algorithm, digest, bytes)` 寻找候选对象。
- 云端摘要是本应用清单记录的数据，不是 iCloud 自动返回的内容证明。
- 只有账号、writer、对象身份、退休状态、上传确认和可用版本信息均符合合同，才可直接复用；元数据发现不完整时保持 pending 或验证，不能凭两个哈希字段相同就宣布文件存在。
- 首次/重新上传需要读原文件；在本来必须发生的复制/上传暂存读取中重算摘要，并与缓存的预期值核对。发现实际字节不同则失败并提示检查，不能覆盖预期摘要、把损坏内容直接变成“新正确值”。
- 复用对象状态有疑问时下载实际内容校验或停止复用；不得以未知状态静默新写一个包含坏数据的完成快照。
- SQLite 快照、manifest、contents 是本次新生成内容，每次都计算准确摘要，不能套用不可变媒体缓存规则。

正常增量备份不是逐字节扫描全部历史媒体的完整健康检查。它建立在不可变存储和已确认记录上；若以后需要主动“检查所有备份”功能，应单独定义成本和界面，不在每次备份隐式执行。

## 6. 恢复校验仍必需

恢复本来就要把文件读到新数据集。原生层从已物化 iCloud 文件复制到准备区时，在同一次流式读取中计算摘要，与选定快照的清单比较；不只是比较两份数据库中的历史摘要。

这样可以避免通常情况下“完整下载/复制后，再为了算 hash 读一遍”的额外全文件扫描。必要的异常重验、重启后对已留存 stage 的重验不能省略。最终发布目标文件仍须成功 flush/close、长度匹配并原子 rename；任一失败不能开放新数据集。

只有实际校验通过，才能标记该下载项 verified 并把摘要登记到新 dataset 的本地缓存。摘要检测的是与备份原始字节的一致性，不能修复原来就损坏的视频，也不能替代数据库结构、迁移和业务数据验证。

## 7. 可执行验证

- H01 导入源只被完整读取一次，同流落盘文件的测试侧独立摘要与缓存一致。
- H02 导入中断、写满磁盘、长度不匹配或 hash 中断不留下有效缓存记录。
- H03 同一不可变文件第二次备份、仅显示改名后备份，不重新读取该媒体全部字节且不重传已确认云对象。
- H04 同名不同内容、同大小不同内容、dataset 切换、原文件替换不能误用旧缓存。
- H05 旧文件第一次补算后，下次可以复用；缓存丢失能重建而不改业务资料。
- H06 云端元数据/对象缺失、上传未确认、账号变化、退休对象，即使摘要字段相同也不能跳过检查。
- H07 上传暂存和恢复复制中的实际摘要失配会拒绝发布/激活；恢复不能只读 manifest 字段就标记 verified。
- H08 静默同大小/mtime 不变的字节损坏，不能被单靠 stat 的快速判断发现；首次上传/恢复实际读字节校验必须发现，验证文案不得宣称快路径已做全量健康扫描。
- H09 大文件处理内存有界、worker 并发有上限、UI 帧时间及耗电/耗时有真机记录；不通过 main isolate 的全量数组或密集进度刷新卡住界面。
- H10 导入后独立测量第一次备份、无变化第二次备份、新增小文件备份和全量恢复；报告读取字节数、hash 用时、总耗时、峰值内存和帧时间，不能用 Mac 数值承诺 iPhone 性能。
